## 已复现的问题

`20261022154243_material_pipeline.sql` 向 `authenticated` 授予 `material_jobs` 表的 `SELECT`、`INSERT` 和 `UPDATE`，行级策略限制所有者，但不限制这些权限所能修改的列。后续仓库迁移未撤销上述授权。

隔离数据库测试中，任务所有者可以将自己的运行中任务改回 `pending`，清空 `calls` 和租约。Worker 随后重新领取该任务，模拟账本允许另一次预留。这说明目前的任务状态与调用次数不能作为防止同一任务重放的可信边界。另一用户修改该任务返回零行；本次没有发现跨用户任务修改的证据。

此外，`material_jobs_api` 是已授权用户可调用的 invoker RPC，其 `submit` 接受调用方提供的任务 `payload`。因此只撤销直接写表权限，再简单把原 RPC 改为 definer，并不能解决问题：调用方仍可能绕过应用服务中的付费确认、配置与输入快照检查。真实可利用性还取决于线上数据库和 Data API 的配置。

## 开关的实际作用

仓库中的 `MATERIAL_PIPELINE_ENABLED` 与 `MATERIAL_WORKER_READY` 默认关闭；材料提交入口及云端模型、图片内部代理受这些开关约束。关闭它们可以阻止经应用入口提交新任务及新的代理请求，但不会撤销已在途请求，也不会限制绕过应用直接访问数据库。

独立材料 Worker 的启动代码并不检查上述就绪开关，且会在自己的进程内设置管线开关。即使应用入口关闭，它仍可能领取数据库中的任务并执行非模型步骤。停止或排空独立 Worker 是单独的运维动作；关闭应用开关不等同于关闭 Worker。不得重放结果或费用尚不确定的任务。现有开关和 Worker 在线上的实际状态本次没有核验。

## 修复需要覆盖的边界

- 任务的状态、租约、调用记录和可信输入必须只能由受限的服务端路径修改；不得让用户通过直接表写入或公开 RPC 伪造执行授权。
- 需要同时保护提交入口和应用结果入口：鉴权用户调用公开 RPC 时，仍须验证任务属于其项目，并且任务快照和付费确认来自可信服务端流程。
- `MaterialJobs.find()`、`material_jobs_api` 的 `raw`、材料应用与产物签名路径当前依赖原有授权。收紧权限前必须替换或调整这些路径，保证正常查询、取消、应用和导出可用，避免意外中断已有任务。
- 隔离 PostgreSQL 回归应覆盖直接重排队和清空调用数被拒绝、伪造提交被拒绝、正常操作、跨用户隔离和租约失效；还需测试真实的计费对账与不确定结果处理，不能仅凭数据库测试声称完成生产验收。

## 仓库内的修复与发布要求

`20261108010000_harden_material_job_authority.sql` 撤销客户端对任务表的直接权限，将敏感操作放入私有 schema 的受限函数，逐次核对账号、项目和独立的服务端能力；普通客户端只能通过受限接口查询或取消自己的任务。服务端能力使用独立的 `MATERIAL_SUBMIT_SECRET`，不得与 Worker 密钥共用；最少 32 个字符，必须使用随机密钥，仅配置在 API 服务端。私有表只保存密钥的 SHA-256 摘要并启用 RLS，迁移本身不包含密钥，未配置时敏感操作保持关闭。正常的手动章节版本仍可保存，但客户端不能为版本指定后台任务 ID；手动版本的 `source` 不是可信审计证据。

旧任务无法证明此前未被篡改：迁移将旧的排队和运行中任务标为待核对并撤销租约；旧完成任务保留原记录与结果，查询投影标为待核对，不能作为可信任务结果应用或获取产物。迁移不会中止已经发给模型服务的请求，相关结果和费用仍需要核对。新任务必须经可信 API 提交，服务端和数据库的配置、调用能力均准备好后才可启用 Worker。

新旧协议不兼容，发布须安排维护窗口：先停止或排空独立 Worker，并关闭应用侧材料入口；保留任务、账单与产物备份，在目标数据库审查并执行迁移，通过安全渠道将服务端密钥的 SHA-256 摘要写入 `material_private.submit_capability`，再将相同密钥配置到 API 服务。密钥不能输出到日志、前端或仓库。完成数据库与 API 的联调、权限和账单核验后，才能重新开启材料入口与 Worker。仅变更环境变量不等于完成数据库修复。

回滚不能简单恢复旧 RPC 或重新授予客户端写表权限，否则会重新引入漏洞。若新版本需要撤回，先关闭材料入口、停止 Worker、保留所有任务与费用记录；使用仍能适配安全权限的服务版本处理人工核对。恢复旧数据库结构或权限之前必须先有单独审计过的替代防护，并在隔离环境验证。数据库迁移与应用代码必须作为一个兼容性单元规划，不可单独上线新客户端。

`tests/test_material_postgres.py` 的隔离回归覆盖历史任务隔离、直接篡改与伪造提交被拒绝、正常提交去重和应用、取消失租以及清理路径限制。测试结果不能证明生产配置已修复。当前工作环境未安装 Supabase CLI，CLI 迁移列表和数据库 advisor 尚未运行；上线前还需在目标环境按实际版本完成检查与真实计费验收。
